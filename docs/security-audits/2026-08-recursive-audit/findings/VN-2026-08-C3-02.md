# VN-2026-08-C3-02 — `case_records` UPDATE policy does not protect `patient_name`, `patient_age`, `patient_sex`, `patient_key`, or `chief_complaint` from re-write by the submitter

**Severity:** HIGH
**Status:** OPEN
**Location:** `backend/supabase/migrations/phase15_data_security_hardening.sql:206-238`
**Component:** Supabase RLS
**Category:** Audit trail integrity / medical record integrity

## Evidence

The `case_records_update_policy` allows the submitter to update their own row. The `WITH CHECK` clause only protects `reviewed_by` (cannot be set by anyone except doctors+). It does **not** protect:

- `patient_name`, `patient_age`, `patient_sex`, `patient_key` (PII fields)
- `chief_complaint`, `observations`, `known_conditions`, `current_medications`, `symptoms` (clinical content)
- `bp_systolic`, `bp_diastolic`, `spo2`, `heart_rate`, `temperature`, `is_pregnant` (vitals)
- `triage_level`, `triage_confidence`, `risk_driver` (ML output)
- `facility_id` (this is the most dangerous — submitter can re-attribute a case to a different PHC)
- `client_id` (idempotency key — submitter can re-use a victim case's id and break dedup)

The Phase 37 `phase37_backfill_submitted_by_trigger.sql` adds an immutability trigger for `submitted_by` (good), but no other field is similarly protected.

## Risk (chained attack)

1. ASHA worker submits an EMERGENCY case with patient PHI.
2. Same ASHA worker (or any RLS-permitted co-worker) calls `PATCH /rest/v1/case_records?id=eq.<id>` with `{"patient_name": "...", "patient_age": 99, "triage_level": "ROUTINE", "facility_id": "<other PHC>"}`.
3. The doctor reviewing the case sees the modified record. The audit trail shows only the *latest* write, and there is no trigger protecting these fields.
4. The case is also now attributed to a different facility (cross-PHC integrity break). The deterioration alert RPC and the team-metrics aggregate silently use the new facility.

The route handlers do not expose `triage_level` or `patient_name` as updatable from the API (the route uses a hardcoded `db.update({reviewed_by, reviewed_at})`), but the Supabase REST API is also directly callable with a valid JWT — RLS is the only backstop.

## Recommendation

Either:
- Add BEFORE UPDATE triggers protecting each clinical/PII column, mirroring the `trg_protect_case_records_submitted_by` pattern.
- Or replace the broad submitter-or-doctor UPDATE policy with narrower, per-action policies (the current `cases.py` route is the only legitimate submitter-update path: changing `deleted_at` for soft delete).
