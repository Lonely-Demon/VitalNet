# VN-2026-08-C3-01 — case_records has NO INSERT RLS policy: every authenticated user can fabricate a case attributed to any other user

**Severity:** CRITICAL (mitigated by app-layer `_resolved_role` + `submitted_by = user["sub"]` write; re-evaluate if those change)
**Status:** OPEN
**Location:** `backend/supabase/migrations/phase15_data_security_hardening.sql:184-238`, plus subsequent migrations
**Component:** Supabase RLS
**Category:** Trust boundary / RLS gap

## Evidence

`phase15` enables RLS on `case_records` and adds SELECT (via `asha_select_own` later rewritten in `phase32`), UPDATE, and DELETE policies, but **never adds an INSERT policy**. `phase32_fix_jwt_metadata_rls_vulnerability.sql` adds the SELECT policy but still does not add INSERT.

`backend/app/api/routes/cases.py::submit_case` writes via the per-user RLS-scoped client, and explicitly sets `submitted_by = user["sub"]` in the record (cases.py:207), so a malicious user cannot directly fabricate a case attributed to another user — yet.

## Risk (chained attack)

An elite attacker can:

1. Bypass the FastAPI layer entirely and POST directly to the Supabase REST endpoint with the RLS-scoped anon key + their own JWT (`POST /rest/v1/case_records`).
2. Submit a case with `submitted_by = ANY_VICTIM_UUID` because nothing in RLS prevents it. The schema constraint is `submitted_by` being NOT NULL (phase15), not foreign-keying the user.
3. The fake case now appears in the victim's case list (`/api/cases/mine` for the victim), in the doctor's dashboard under the victim's facility, and in the audit log as if the victim submitted it — the entire integrity chain is compromised.

The mitigation is the FastAPI route doing the `submitted_by = user["sub"]` overwrite. If anyone writes a new route that accepts `submitted_by` from a request body (e.g., for "transferring" a case), or if a future maintainer reorders the `.update()` to use a user-supplied value, the attack becomes trivial. This is a classic "defense in depth is missing" finding.

## Recommendation

Add a WITH CHECK INSERT policy on `case_records`:

```sql
CREATE POLICY case_records_insert_policy ON public.case_records
  FOR INSERT TO authenticated
  WITH CHECK (
    submitted_by = auth.uid()
    AND EXISTS (
      SELECT 1 FROM public.profiles p
      WHERE p.id = auth.uid()
        AND p.is_active
        AND (
          p.role IN ('admin')
          OR (p.role = 'asha_worker' AND p.facility_id = facility_id)
        )
    )
  );
```

That way the integrity constraint is enforced by the database, not by whichever Python route happens to remember to set `submitted_by = user["sub"]`.
