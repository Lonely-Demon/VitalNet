# VN-2026-08-C8-02 — `apps/api` is not covered by Dependabot; Deno deps are a known unmonitored supply-chain surface

**Severity:** MEDIUM
**Status:** OPEN (acknowledged in docs/SECURITY.md / dependabot.yml)
**Location:** `.github/dependabot.yml` (apps/api omitted)
**Component:** Supply chain
**Category:** Missing coverage

## Evidence

```yaml
# NOT covered by Dependabot: apps/api (Deno/Hono). Deno is not a supported
# Dependabot ecosystem — its deps (deno.lock) need a manual review cadence or
# a Renovate config; tracked as a known gap in docs/SECURITY.md.
```

The `apps/api` is the **new** backend (Deno + Hono, deployed to Supabase
Edge Functions). It depends on `jose`, `@supabase/supabase-js`,
`hono`, etc. (per `_shared/auth.ts` and others). It is *not* served
by the legacy FastAPI backend (which is the one being kept alive and
audited). As the migration progresses, the live-traffic backend will
be `apps/api`, not `backend/`.

## Risk (chained attack)

1. A vulnerability in `jose` (the JWT library) is published; the
   legacy backend auto-updates via Dependabot.
2. The same vulnerability exists in the `apps/api` version of `jose`,
   but there is no Dependabot PR because apps/api is not monitored.
3. The team migrates `/api/submit` to `apps/api` (it's already a key
   in `ENDPOINT_BACKEND`).
4. Production traffic now hits the vulnerable `apps/api`.
5. Attacker exploits the `jose` CVE against the production edge
   function.

The same pattern applies to any other Deno dep: `hono`, `npm:react`,
the Supabase JS client, etc.

## Recommendation

1. Add a Renovate config for `apps/api` (renovate supports Deno via
   `deno.lock`).
2. Or, run a weekly `deno outdated` job in CI and open a manual PR
   for any flagged version.
3. Document the SLA in `docs/SECURITY.md`: a CVE in a Deno dep
   triggers an out-of-band PR within 24h.
4. Pin the Deno stdlib version explicitly in CI.
