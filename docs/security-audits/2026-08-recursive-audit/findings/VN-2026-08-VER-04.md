# VN-2026-08-VER-04 — Rate-limit bucket collision under reverse proxies (CONFIRMED, with refinement)

**Severity:** MEDIUM
**Status:** OPEN
**Location:** `backend/app/api/routes/cases.py:29-41`, `backend/app/core/auth.py:203-211`
**Component:** Backend
**Category:** DoS via cross-user rate-limit sharing

## Evidence

```python
# cases.py:29-41
def _get_user_id(request: Request) -> str:
    auth_header = request.headers.get("authorization", "")
    token = auth_header.split(" ", 1)[-1] if auth_header else ""
    sub = verify_sub_for_rate_limit(token) if token else None
    return sub or (request.client.host if request.client else "unknown")
```

```python
# auth.py:203-211
def verify_sub_for_rate_limit(token: str) -> str | None:
    payload = _decode_local(token)  # HS256-only!
    return payload.get("sub") if payload else None
```

`verify_sub_for_rate_limit` only attempts the HS256 fast path. For Supabase
projects using asymmetric (ES256/RS256) signing keys (the *default* for new
Supabase projects since 2024), `_decode_local` returns `None` and the rate
limiter falls back to `request.client.host`.

Behind a reverse proxy (Railway, Fly, Nginx, Cloudflare), `request.client.host`
is the **proxy's** IP, not the client's. Every authenticated user behind the
proxy shares a single rate-limit bucket.

## Risk (chained attack)

1. Production deployment uses asymmetric Supabase keys + a reverse proxy.
2. A burst of N legitimate ASHA workers (N=20) from the same clinic hit
   `submit_case` simultaneously. Their 20 req/min buckets are not differentiated
   by user; they all share the proxy's IP bucket.
3. SlowAPI's per-process in-memory store is now a *single* bucket of 20/min
   across N users → first 20 requests succeed, the rest 429.
4. Real EMERGENCY submissions get rate-limited.

The verifier's recommendation ("extract the unverified sub from the JWT for the
rate limit key after full cryptographic verification") is partially correct
but the *mechanism* matters: extracting the sub from the *already-verified*
JWT requires the `key_func` to run *after* route-level auth. SlowAPI's
`key_func` runs in middleware before the route. The right fix is:

1. Extend `verify_sub_for_rate_limit` to also try the asymmetric path (JWKS
   verify), or
2. Move the rate limiter to run *after* the route's auth dependency (using
   a custom `Depends(get_current_user)` to derive the key), or
3. Use Starlette's `X-Forwarded-For` correctly (validate the proxy chain, then
   use the *real* client IP) so the IP-based bucket matches the NATed clinic.

The cleanest fix: in `verify_sub_for_rate_limit`, accept both algorithms
(mirror the apps/api `_shared/auth.ts::verifyToken` pattern).

## Recommendation

```python
# auth.py
def verify_sub_for_rate_limit(token: str) -> str | None:
    # Try HS256 first (fast), then JWKS (covers asymmetric-key projects).
    payload = _decode_local(token)
    if payload is None:
        # Mirror the apps/api path: also try JWKS for asymmetric-key projects.
        try:
            import httpx
            jwks_url = f"{settings.supabase_url}/auth/v1/.well-known/jwks.json"
            jwks = httpx.get(jwks_url, timeout=2).json()
            for key in jwks.get("keys", []):
                try:
                    from jose import jwt as jose_jwt
                    payload = jose_jwt.decode(
                        token, key,
                        algorithms=[key["alg"]],
                        audience="authenticated",
                    )
                    break
                except Exception: continue
        except Exception: return None
    return payload.get("sub") if payload else None
```

This is more expensive (a JWKS fetch per request) — cache the JWKS.
