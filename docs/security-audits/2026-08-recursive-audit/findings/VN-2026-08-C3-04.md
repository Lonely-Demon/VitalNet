# VN-2026-08-C3-04 — `case_reviews_immutable CHECK (true)` is a comment, not a constraint

**Severity:** MEDIUM
**Status:** OPEN
**Location:** `backend/supabase/migrations/phase15_data_security_hardening.sql:176`
**Component:** Supabase RLS
**Category:** Audit trail integrity

## Evidence

```sql
CREATE TABLE IF NOT EXISTS public.case_reviews (
  id uuid PRIMARY KEY DEFAULT gen_random_uuid(),
  case_id uuid NOT NULL REFERENCES public.case_records(id) ON DELETE CASCADE,
  reviewer_id uuid NOT NULL REFERENCES public.profiles(id) ON DELETE RESTRICT,
  reviewed_at timestamptz NOT NULL DEFAULT timezone('utc', now()),
  note text,
  CONSTRAINT case_reviews_immutable CHECK (true)  -- Marker for immutability intent
);
```

The constraint expression is `CHECK (true)`. It accepts every row. The
intent comment ("Marker for immutability intent") is honest about this being
a no-op.

In addition, no RLS UPDATE or DELETE policy exists on `case_reviews`. RLS
default for tables with RLS enabled is to deny everything; the absence of an
UPDATE/DELETE policy means no one (including admin via the per-user client)
can update or delete, which is the *intent*. But:

1. The `supabase_admin` service-role client bypasses RLS — a real risk if a
   future bug lets a non-admin path use the service-role key.
2. There is no trigger preventing UPDATE/DELETE on the table, so a future
   `ALTER TABLE ... DISABLE ROW LEVEL SECURITY` or a misconfigured
   service-role call would have no other backstop.

## Recommendation

Replace the marker constraint with a real immutability trigger, mirroring
`trg_protect_case_records_submitted_by`:

```sql
CREATE FUNCTION case_reviews_immutable() RETURNS trigger AS $$
BEGIN
  RAISE EXCEPTION 'case_reviews is append-only';
END;
$$ LANGUAGE plpgsql;
CREATE TRIGGER trg_case_reviews_no_update BEFORE UPDATE ON case_reviews
  FOR EACH ROW EXECUTE FUNCTION case_reviews_immutable();
CREATE TRIGGER trg_case_reviews_no_delete BEFORE DELETE ON case_reviews
  FOR EACH ROW EXECUTE FUNCTION case_reviews_immutable();
```
