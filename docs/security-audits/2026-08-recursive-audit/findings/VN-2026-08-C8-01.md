# VN-2026-08-C8-01 — `pnpm/action-setup@v4` is a tag, not a commit SHA — supply-chain attack vector

**Severity:** MEDIUM
**Status:** OPEN
**Location:** `.github/workflows/ci.yml:55, 94, 165, 198`
**Component:** CI/CD
**Category:** Supply chain

## Evidence

```yaml
- uses: pnpm/action-setup@v4  # TODO: pin to a verified commit SHA to match this repo's other actions (see docs/SECURITY.md "Dependency management")
```

The team has a TODO acknowledging this gap. The same workflow has
correctly pinned `actions/checkout@9c091bb21b7c1c1d1991bb908d89e4e9dddfe3e0`
and `actions/upload-artifact@043fb46d1a93c77aae656e7c1c64a875d1fc6a0a` to
commit SHAs (good). The `pnpm/action-setup@v4` is a moving tag.

A malicious or compromised pnpm maintainer (or anyone who gains
write access to the `pnpm/action-setup` repo) can push a new commit
to the v4 branch, and the next CI run will pull it without any review
or PR. The CI job runs with `secrets.TEST_SUPABASE_*` available
(though the build-frontend-pr job deliberately does *not* receive them,
the test-backend job does).

## Risk (chained attack)

1. Attacker compromises `pnpm/action-setup` repo.
2. Pushes a commit to the v4 branch that exfiltrates environment
   variables (in the test-backend job: Supabase URL, anon key, JWT
   secret, service_role key, Groq API key).
3. CI runs, secrets are exfiltrated.
4. Attacker now has the **service_role key** to a real Supabase project
   (the test project, but if the same env is reused for production
   smoke tests, also production).
5. Service-role key = bypass RLS = full PHI access.

The `test-backend` job runs `if: github.event_name == 'push'` (not
PR), so the secret exposure is on push to main/dev/test, which is
post-merge. But CI still runs on those branches.

## Recommendation

1. Pin `pnpm/action-setup` to a specific commit SHA, matching the
   pattern used for the other actions.
2. Use a "stale action" detector (`rhysd/actionlint`,
   `step-security/harden-runner`) to fail CI on any unpinned action
   reference.
3. Document the policy in `docs/SECURITY.md` with an explicit list of
   which actions must be SHA-pinned and which may be tag-pinned (with
   justification).
