# VN-2026-08-C4-01 — Auth context reads `app_metadata.role` from JWT — direct contradiction of the backend's "never trust user_metadata" rule

**Severity:** HIGH
**Status:** OPEN
**Location:** `apps/web/src/store/authStore.jsx:77`
**Component:** Frontend
**Category:** Defense-in-depth failure / role confusion

## Evidence

```jsx
// authStore.jsx
role: session?.user?.app_metadata?.role ?? profile?.role ?? null,
```

The backend (backend/app/core/auth.py:24-29) explicitly says:

> Authorization fields: role and facility_id are NEVER trusted from the JWT's
> user_metadata — that's client-settable at signup and can go stale for the
> life of the token after an admin changes it. Every request resolves fresh
> values from the profiles table

The backend route guards in `app/api/routes/cases.py` etc. use
`user.get("resolved_role")` — the freshly-resolved value, not the JWT
claim. So the *server* is correct.

But the *frontend* AuthContext exposes a `role` that is `app_metadata.role`
first, falling back to `profile.role` (the cached profiles row, not the
freshly-resolved one). Anything on the client that branches on this `role`
is making a security decision on a value the backend documents as
untrustworthy.

## Risk (chained attack)

1. Admin demotes an ASHA worker to nothing (deactivates their account, or
   re-roles them) — but the worker's token still has the old
   `app_metadata.role`.
2. The frontend AuthContext's `role` is still the old value. Components
   like `RouteGuard.jsx` and `NavBar.jsx` may gate UI on this client-side
   `role`, and the user sees admin/doctor UI.
3. The *actual* backend call still 403s (because `resolved_role` is the
   fresh value), so no data leak — but the UI shows pages the user has
   no access to, and the worker can probe UI affordances that don't
   exist. Worse, a worker who *was* never an admin but whose JWT was
   somehow forged (or whose session was hijacked) sees the admin UI.
4. Combined with the `clearSharedDeviceState` race: a session token can
   outlive the worker's auth (it does, by design — the project relies on
   the in-process `_profile_cache` to demote). During the demotion
   window, the worker's UI shows the old role.

## Recommendation

1. The frontend should *not* expose a single `role` field that mixes
   `app_metadata` and `profile.role`. Either:
   - Make `role` always come from `profile.role` (the cached-but-fetched
     value), and have a `jwtRole` separate field for diagnostic use.
   - Or re-fetch the profile on every render path that branches on
     role, and never trust the cached profile either.
2. Add a route-guard test that mocks an admin-only render path with a
   `app_metadata.role = 'admin'` but `profile.role = 'asha_worker'`, and
   asserts the admin UI is *not* shown.
3. The frontend cannot truly enforce role-gated UI; the backend must
   always be the source of truth. Document this with a per-component
   `data-testid` and a comment that this is *only* for UX, not security.
