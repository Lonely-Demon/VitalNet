# VN-2026-08-C4-03 — Outbox owner_id check happens client-side only — a malicious local script can submit under another worker's JWT

**Severity:** HIGH
**Status:** OPEN
**Location:** `apps/web/src/lib/outbox.js:74-79, 125-130`
**Component:** Frontend
**Category:** Trust boundary

## Evidence

```js
// outbox.js
export async function getPendingEvents(ownerId) {
  if (!ownerId) return []
  const db = await getOfflineDB()
  const all = await db.getAllFromIndex(STORE_NAME, 'created_at')
  return all.filter((e) => e.status === 'pending' && e.owner_id === ownerId)
}
```

The `owner_id` check is in JavaScript, against a *local* IndexedDB. The
`owner_id` is set when the row is enqueued:

```js
await db.put(STORE_NAME, {
  event_id: eventId,
  owner_id: ownerId ?? null,
  ...
})
```

A worker who logs in to a shared device can:
1. Open DevTools, find the IndexedDB `outbox` store, and read every
   queued row (patient PHI in the payload).
2. Modify `owner_id` to their own auth user id.
3. Force `syncStore.js` to drain the outbox, which now sends another
   worker's patient data under the new worker's JWT.

The submit endpoint (`/api/submit`) sets `submitted_by = user["sub"]` —
the *current* worker's user id. The server has no way to know the row
was originally queued by someone else.

## Risk (chained attack)

This is a real PII exfiltration + mis-attribution attack:
- Attacker (Worker B) reads Worker A's queued case (PHI: patient name,
  chief complaint, vitals) directly from IndexedDB on a shared PHC
  tablet.
- Attacker rewrites `owner_id` and forces a drain.
- The case is submitted to the server with `submitted_by = B's user id`.
- A's queued case no longer exists (it was dequeued). A has no record
  of having queued it (the IndexedDB row is gone).
- The doctor's UI shows the case as "submitted by B."
- B has a copy of A's patient PHI in the IndexedDB write history (and
  in the network logs if B exfiltrates via `navigator.sendBeacon`).

## Recommendation

1. **Don't store the patient payload in the outbox unencrypted.** The
   payload contains PII. Encrypt it with a worker-bound key (e.g.,
   derived from the worker's `sub` via a key-derivation function), so a
   worker with a different `sub` cannot read the payload even if they
   read the IndexedDB.
2. **Server-side owner validation.** On `/api/submit`, require the
   `X-Event-Id` (which is `client_id`) to match `submitted_by` in some
   deterministic way — e.g., compute a per-user HMAC of the event id on
   enqueue and verify it on submit. The current design uses
   `client_id` (a UUID) as the idempotency key but no
   authenticity check.
3. **Audit log on the server.** The current `submit_case` audit log
   records `user_id = user["sub"]` — but if the worker is compromised,
   this is the *attacker's* user id. Adding a per-device fingerprint
   (the `X-Device-Id` header is already required) and a per-event
   `X-Event-Id` correlation makes the chain reconstructable.
4. **Document the shared-device trust model in `authStore.jsx`.** The
   project explicitly relies on the PHC tablet being physically
   controlled by a single worker at a time. The "shared device" model
   assumes the OS-level user separation, not application-level
   isolation. The current code does not communicate this to the
   worker, and does not enforce it.
