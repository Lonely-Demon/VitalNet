# VN-2026-08-C5-01 — `idempotent` middleware reads `c.get("user")` without verifying the middleware order; non-trivial crash class

**Severity:** MEDIUM
**Status:** OPEN
**Location:** `apps/api/supabase/functions/api/_shared/idempotency.ts:36-77`
**Component:** apps/api
**Category:** Middleware-order contract violation

## Evidence

```ts
export function idempotent(eventType: string) {
  return async (c: Context<AppEnv>, next: Next) => {
    const eventId = c.req.header("X-Event-Id");
    if (!eventId || !UUID_RE.test(eventId)) {
      await next();
      return;
    }
    const user = c.get("user");
    const db = getSupabaseForUser(user.token);
    // ...
  };
}
```

The docstring says "Must be registered AFTER requireRole()". But the code
does not check `user` is defined. If a future maintainer registers
`idempotent` before `requireRole`, or on a route that has no
`requireRole`, `c.get("user")` is `undefined`, `user.token` throws
`TypeError: Cannot read properties of undefined (reading 'token')`, and
the edge function crashes with a 500.

The bigger risk: `requireRole` is the function that calls
`getCurrentUser`, which calls `verifyToken`. The Deno edge function
treats a thrown TypeError as a 500 with the body suppressed by Hono's
default error handler. There is no `try/catch` here, so a missing
`requireRole` is *silent* at the route level — the call fails opaquely
instead of returning a clean 401.

## Risk (chained attack)

1. An elite attacker finds an endpoint that has `idempotent("case.submit")`
   but is missing `requireRole` (a future refactor mistake).
2. The attacker calls the endpoint with their own JWT in the
   Authorization header *and* a valid X-Event-Id.
3. `c.get("user")` is undefined → 500.
4. But the `getSupabaseForUser(user.token)` happens *before* the next()
   call. The middleware tries to look up `client_events` for that event
   id. If the event id already exists (the attacker has tried it
   before), the SELECT succeeds, returns the prior response (which
   may include PHI from a *different* user's prior submission), and
   returns it to the attacker. The `submitted_by = auth.uid() OR admin`
   RLS policy should prevent this — but the lookup is happening under
   the attacker's own auth context, so they only see rows they own.
5. The attacker can submit one valid request, get a successful event_id,
   then probe other endpoints to find one that reads the response and
   re-emits it.

The real risk is a missing `requireRole` *plus* the use of
`c.get("user").token` outside of its proper chain. The current
codebase is consistent (`requireRole` precedes `idempotent` everywhere),
but the contract is not enforced.

## Recommendation

1. Add a runtime check in `idempotent`:
   ```ts
   const user = c.get("user");
   if (!user?.token) {
     throw new HttpError(500, "idempotent middleware requires requireRole upstream");
   }
   ```
2. Make `idempotent` a method on the route *factory* that requires
   `user` to be set, so the type system enforces the contract.
3. Add a regression test that mounts the routes without `requireRole`
   and asserts an explicit 500 (not a TypeError).
