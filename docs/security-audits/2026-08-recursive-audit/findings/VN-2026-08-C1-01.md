# VN-2026-08-C1-01 — CSRF token is a hard-coded literal, not a server-side secret

**Severity:** MEDIUM
**Status:** OPEN
**Location:** `backend/app/main.py:57,131-135` and `backend/app/core/config.py:57`
**Component:** Backend (FastAPI middleware)
**Category:** CSRF / defense-in-depth

## Evidence

```python
# backend/app/core/config.py:57
csrf_token: str = "vitalnet-spa"

# backend/app/main.py:131-135
csrf_header = request.headers.get("x-csrf-token", "")
if csrf_header != settings.csrf_token:
    return JSONResponse(
        status_code=403, content={"detail": "CSRF token missing or invalid"}
    )
```

The same literal is used for every backend deployment, every environment, and
every user. The comment in `config.py` is correct that the value is "not a
secret — the protection comes from the CORS preflight" — but the *implementation*
treats it as a secret comparison (`!=`), and the constant value is shipped in
the open-source tree, so anyone who clones the repo knows the expected value.

The defence-in-depth header requirement is still useful (it forces a CORS
preflight, which the `allow_origins` allowlist constrains), but the comparison
is a tautology: an attacker on an attacker-controlled origin will fail CORS
anyway; an attacker on an allowlisted origin (compromised web app) can read
the constant.

## Risk

- No real-world bypass today (CORS preflight is the real gate), but the
  constant is documented as "the protection comes from the CORS preflight"
  while the code does an equality comparison that *looks like* a secret match.
  The false sense of security is a maintainability/security-debt risk.
- If a future maintainer adds a non-allowlisted origin to the dev allowlist and
  the same constant ships in the wild, the CSRF check is no longer a
  defence-in-depth net.

## Recommendation

Either:

1. Drop the equality check entirely and just require the *presence* of the
   header (a custom-header preflight is what the comment claims is the gate).
   That keeps the behaviour as advertised.
2. Per-session/per-user CSRF token issued on login, stored server-side, with
   the header carrying a real session-bound value. This is what real
   "double-submit" or "synchronizer" CSRF defences look like.

Mark the constant as "intentionally static" or remove it; do not ship a
shipped-with-the-repo value that is *compared* like a secret.
