# VN-2026-08-C7-01 — `triage_classifier.pkl` is unpickled at startup; pickle RCE is a real concern if the model file is ever substituted

**Severity:** HIGH (supply-chain dependent)
**Status:** OPEN (mitigated by signature verification recommendation)
**Location:** `backend/app/ml/classifier.py:34, 141-200` (load_classifier)
**Component:** Backend / ML
**Category:** Deserialization RCE

## Evidence

```python
PKL_PATH = Path(__file__).parent / "models" / "triage_classifier.pkl"
...
def load_classifier() -> bool:
    global _classifier, _explainer, _feature_names, _label_map, _model_version, _performance_metrics
    if not PKL_PATH.exists():
        raise RuntimeError(...)
    ...
    with open(PKL_PATH, "rb") as f:
        bundle = pickle.load(f)
```

Python's `pickle.load` is well-known to allow arbitrary code execution
via `__reduce__`. The `.pkl` is committed to the repo (per
`backend/app/ml/README.md`) and loaded at every app startup.

A successful attacker who can:
1. Modify the `.pkl` file (write access to the repo or the deployed
   image), or
2. Compromise the training pipeline (`tools/training/train_classifier.py`)
   to inject a malicious pickle payload,

…can run arbitrary Python code in the API process at next startup. This
is a *complete* server compromise (PHI exfiltration, RLS bypass via the
service-role key, all databases).

## Risk (chained attack)

1. Attacker compromises a developer's GitHub PAT (e.g., via a phishing
   campaign targeting the small VitalNet dev team).
2. Pushes a commit that replaces `triage_classifier.pkl` with a
   malicious pickle (the binary diff is small).
3. CI runs `pytest`, which doesn't unpickle the model unless the test
   path triggers `load_classifier()`. The malicious pickle sits.
4. Production deploys; the new container starts, calls
   `load_classifier()`, the pickle's `__reduce__` runs, attacker has
   shell.
5. The attacker now has access to `supabase_service_role_key` from the
   container's environment, plus the postgres connection. Every patient
   record is exfiltrated.

The training pipeline is also a target. `train_classifier.py` writes the
`.pkl`. If the training pipeline is compromised (e.g., a malicious
`train_classifier.py` change that adds `__reduce__` to the bundle dict),
the next training run produces a weaponized `.pkl`.

## Recommendation

1. **Sign the .pkl**. Use `python-jose` (already a dependency) to sign
   a SHA-256 hash of the `.pkl` with a key stored *only* in the
   deployment environment. On load, verify the signature; refuse to
   load if the signature doesn't match.
2. **Use a safer serialization format** for the model. The tree-based
   model can be exported to ONNX, JSON (which `tree_export.py` already
   does for the browser), or `joblib` with restricted `__reduce__`
   policies. Pickle is the most dangerous default.
3. **Pin a hash** in `requirements.txt` style for the `.pkl`:
   `triage_classifier.pkl.sha256: abc123...`. Refuse to load if the
   hash doesn't match.
4. **CI check**: the CI job that runs `pnpm --filter @vitalnet/clinical-core build && cd tools/training && python train_classifier.py` should
   also diff the resulting `.pkl` against the committed one and fail
   if they differ (a model-regeneration PR must update the committed
   `.pkl`).
