# VN-2026-08-C7-02 — SHAP TreeExplainer runs per-prediction in the request hot path; the explainer is built from the (untrusted) .pkl

**Severity:** MEDIUM
**Status:** OPEN
**Location:** `backend/app/ml/classifier.py` (load_classifier body)
**Component:** Backend / ML
**Category:** Latent attack surface / DoS

## Evidence

The classifier module loads `_explainer = shap.TreeExplainer(classifier)`
once at startup, then calls `_explainer.shap_values(features)` on every
prediction in `predict_triage()`. The SHAP library version is pinned
exactly (`shap==0.51.0`) per the requirements.txt comment.

SHAP is a heavy compute path. For a single prediction on the
`HistGradientBoostingClassifier`, it's microseconds, but the
combination of:
- A per-request SHAP call in the request hot path
- No request-level timeout on the ML inference

…means a caller can submit cases with pathological feature vectors
(many missing values, extreme outliers) that cause SHAP to take
significantly longer than typical.

## Risk (chained attack)

1. Attacker writes a small script that submits `submit_case` requests
   with carefully chosen vitals to maximize SHAP compute time.
2. Each request holds a worker for several seconds. With a low
   concurrency limit, the worker pool exhausts.
3. Legitimate ASHA workers see timeouts, fail to submit, real EMERGENCY
   cases are delayed.

This is a single-resource DoS, not a data exfiltration. The mitigation
in place (rate limiting) is per-user, so the attacker would need many
users (or one admin's JWT).

## Recommendation

1. Add a `concurrent.futures` timeout to the SHAP call in
   `predict_triage`. If SHAP takes >50ms, fall back to a simpler
   attribution (e.g., permutation importance cached at training time).
2. Cache SHAP values for the *most common* feature vectors (e.g., 100
   most-frequent presentations), so the typical ASHA case hits a
   cache. Only the unusual cases pay the SHAP cost.
3. Move SHAP off the request path: compute it in a background task
   after the case is saved, and write the attribution to
   `case_records.risk_driver` asynchronously. The doctor's UI sees the
   attribution when it's ready (usually <1s later).
