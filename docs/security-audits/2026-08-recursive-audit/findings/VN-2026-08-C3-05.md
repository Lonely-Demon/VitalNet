# VN-2026-08-C3-05 — `auth.uid()` returns NULL for anon; `EXISTS (...)` then short-circuits to NULL, which is falsy — but `=` comparisons misbehave

**Severity:** MEDIUM
**Status:** OPEN (defense-in-depth)
**Location:** all RLS policies
**Component:** Supabase RLS
**Category:** Subtle RLS semantic bug

## Evidence

Almost every RLS policy in the codebase has the form:

```sql
USING (
  (deleted_at IS NULL) AND (
    (submitted_by = auth.uid())
    OR EXISTS (SELECT 1 FROM public.profiles p WHERE p.id = auth.uid() AND ...)
  )
)
```

The `submitted_by = auth.uid()` clause evaluates to NULL when `auth.uid()` is
NULL (i.e., the caller is `anon` or `service_role`). In SQL, `NULL = NULL` is
NULL, not true. The `EXISTS` subquery similarly uses `p.id = auth.uid()`,
which is NULL — but `EXISTS` only checks whether the subquery returns ≥ 1
row, so the inner `p.id = auth.uid()` will not match any profile (since
profile.id is never NULL), so `EXISTS` correctly evaluates to FALSE for an
anon caller.

This *happens* to be the right behavior for the current policy tree — anon
is denied. But the project has previously been bitten by RLS relying on
`user_metadata.role` (phase32). The pattern `column = auth.uid()` is fragile:
if a future maintainer adds `OR auth.uid() IS NULL` somewhere, anon suddenly
has access. Or if they write a `WITH CHECK (col = auth.uid())` policy, the
insert fails for anon (good) but a service-role migration that wants to
insert on behalf of an anon user would fail too.

The bigger risk is the `p.id = auth.uid()` inside the EXISTS: if a maintainer
moves the role/facility check from `EXISTS (SELECT ... WHERE p.id =
auth.uid())` to a JOIN on `auth.jwt() -> 'app_metadata' -> 'role'`, the
fragility returns.

## Risk

- Defence-in-depth is not symmetric. A maintainer adding a new INSERT or
  UPDATE policy on `case_records` for an "anon can submit" use case (e.g.,
  a public intake form) will find their policy silently failing because
  `EXISTS (SELECT 1 FROM profiles WHERE id = auth.uid())` returns no rows
  for anon.
- A maintainer copying the role check pattern to a new table can introduce
  a TOCTOU between `EXISTS` and the actual mutation if they rewrite the
  `WITH CHECK` clause naively.

## Recommendation

- Add a CI test that creates an anon client, attempts every documented
  operation, and verifies denial with a 401/403/PostgREST 403.
- Document the policy in `AGENTS.md` / `docs/RFC_RLS_GUIDE.md` (does not
  exist) so future agents don't paste fragile patterns.
- Add a regression suite that validates every `EXISTS (SELECT 1 FROM
  profiles p WHERE p.id = auth.uid() ...)` query is paired with the
  `p.is_active` check, matching the existing `get_current_user` fail-closed
  contract (auth.py:139-142).
