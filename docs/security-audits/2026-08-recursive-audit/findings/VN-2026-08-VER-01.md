# VN-2026-08-VER-01 — DSR export and erase cross-tenant IDOR (CONFIRMED, also affects Deno edge function)

**Severity:** CRITICAL
**Status:** OPEN
**Location:**
- Python: `backend/app/api/routes/dsr_routes.py:46-105, 108-156`
- Deno: `apps/api/supabase/functions/api/routes/dsr.ts:42-91, 100-137`
**Component:** Both backends
**Category:** Cross-tenant authorization bypass / PHI exposure / destructive

## Evidence

The DSR (Data Subject Request) endpoints are gated only by `require_role("admin")` and
use the *bypass* client `supabase_admin` / `getSupabaseAdmin()` throughout. There is
**no facility-scope check** in either backend.

`dsr_routes.py::_fetch_case_or_404` (line 46-57):
```python
def _fetch_case_or_404(case_id: str) -> dict:
    result = (
        supabase_admin.table("case_records")
        .select("*")
        .eq("id", case_id)
        .maybe_single()
        .execute()
    )
    row = result.data if result else None
    if not row:
        raise HTTPException(status_code=404, detail="Case not found")
    return row
```

`export_case_data` and `erase_case_data` both call this with no facility-scope check
and proceed. `dsr.ts::fetchCaseOr404` is the identical pattern in Deno.

## Risk (chained attack)

1. PHC Admin A authenticates against the system (their own PHC).
2. They call `GET /api/admin/cases/<UUID-of-case-at-PHC-B>/export`.
3. `_fetch_case_or_404` returns the case row from PHC B (RLS bypassed via
   service-role).
4. The function joins `case_outcomes`, `case_attachments`, and `referrals` for the
   same case and returns the full bundle — patient demographics, vitals, clinical
   notes, referral reason, attachments list.
5. Attacker now has PHI for a patient at PHC B.
6. Same for `POST /api/admin/cases/<UUID>/erase` — the attacker can redact
   PHC B's clinical records. The audit log records `user_role = "admin"` (the
   attacker's role at PHC A), `facility_id = PHC B's id` (the case's facility).
   The cross-facility nature of the attack is visible in the audit log, but the
   damage is done.

This is the DSR equivalent of chain A in the original audit — bypass RLS for
legitimate admin reasons, but never re-scope per caller's facility.

## Recommendation

In both backends, before returning or mutating the case:

```python
if user.get("resolved_role") != "supervisor" and case.get("facility_id") != user.get("resolved_facility_id"):
    raise HTTPException(status_code=403, detail="Not authorized for cases outside your facility")
```

`purge_expired` should additionally scope the candidate query to the caller's
facility (or only be invokable by a supervisor).
