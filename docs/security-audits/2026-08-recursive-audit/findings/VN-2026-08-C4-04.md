# VN-2026-08-C4-04 — `clearSharedDeviceState` is best-effort and not awaited before signOut completes

**Severity:** MEDIUM
**Status:** OPEN
**Location:** `apps/web/src/store/authStore.jsx:18-28, 81-87`
**Component:** Frontend
**Category:** Race condition / PII leak on shared device

## Evidence

```jsx
signOut: async () => {
  // Tear down device-local PHI before ending the session (see
  // clearSharedDeviceState). Teardown never blocks sign-out: even if the
  // local clear fails, the session must still end.
  await clearSharedDeviceState()
  return supabase.auth.signOut()
}
```

The comment says "Tear down device-local PHI before ending the session"
and "Teardown never blocks sign-out." These two are in tension:

1. `clearSharedDeviceState` is awaited *before* `supabase.auth.signOut()`.
2. But `supabase.auth.signOut()` triggers an `onAuthStateChange` event,
   which re-runs the *new* worker's profile fetch if the new worker
   logs in immediately.
3. The "form-drafts" clear in `clearSharedDeviceState` does `db.clear('form-drafts')` — this clears drafts for *everyone*, not just the signing-out worker. If two workers are racing logout/login (shared device, fast handover), worker A's logout can clear worker B's still-active draft.

The clear is owner-unaware: it deletes all rows in `form-drafts` regardless of which worker created them.

## Risk (chained attack)

1. Worker A signs out, `clearSharedDeviceState` starts clearing
   `form-drafts`.
2. Worker B, who has an *active* in-progress form, signs in immediately.
3. Worker B's profile fetch is in flight, `localStorage.setItem('vn_facility_phone', B's PHC)`.
4. Worker A's `db.clear('form-drafts')` fires — clears B's draft too.
5. Worker A's `supabase.auth.signOut()` completes.
6. Worker B sees a "fresh" intake form, not their saved draft.

This is a denial-of-service on the worker's draft persistence, not
a confidentiality issue, but:

- The drafts contain PII (patient_name, chief_complaint). If the clear
  fails silently (the try/catch in `clearSharedDeviceState` swallows
  the error), the drafts remain in IndexedDB and are reachable by the
  next worker.
- Conversely, if the clear succeeds but `signOut` fails (e.g.,
  network error), the session is still active but drafts are gone.

## Recommendation

- Scope the draft clear to the signing-out worker's profile id (the
  draft store keys by `draft-{clientId}` today; the clear should
  iterate only drafts owned by `profile.id`).
- Add an `await` ordering: do the `supabase.auth.signOut()` *first*
  (it terminates the JWT, which is the actual auth boundary), and
  only then clear the local data.
- Treat the device-state clear as best-effort but observable: log to
  the audit server (a non-PHI event log) so the failure is visible.
