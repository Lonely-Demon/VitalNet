# VN-2026-08-C3-06 — `fn_schema_fingerprint` is callable by any `authenticated` admin and reveals schema state

**Severity:** LOW
**Status:** OPEN
**Location:** `backend/supabase/migrations/phase28_security_definer_fns.sql:319-365`
**Component:** Supabase RLS / RPC
**Category:** Information disclosure

## Evidence

```sql
GRANT EXECUTE ON FUNCTION public.fn_schema_fingerprint() TO authenticated, service_role;
```

The function returns an MD5 fingerprint. That's not super sensitive. But
the body runs:

```sql
SELECT string_agg(
  conrelid::regclass::text || '.' || conname || ':' || pg_get_constraintdef(oid),
  ...
) FROM pg_constraint
WHERE connamespace = 'public'::regnamespace;
```

The *return value* is an MD5 hash, but the *side effects* are zero (no
NOTICE, no log). The admin check (`v_role IS DISTINCT FROM 'admin'`) is
correct.

The real risk is that the function is `SECURITY DEFINER` and runs with the
function owner's privileges. It calls `pg_constraint` and `pg_policies`,
which are normally visible to anyone with the `pg_read_all_settings` /
`pg_stat_*` grants, but a SECURITY DEFINER function's own audit trail
inside the database does not record "this admin called fn_schema_fingerprint
at time T." That itself is fine, but combined with the
`fn_schema_fingerprint` being the only way to learn "did someone modify the
schema outside of a tracked migration?", an admin who deliberately
modifies the schema and then calls this function to compute the new
fingerprint has no audit trail of *their* call.

## Risk

- Side-channel: the function's existence is documented in a migration, so
  an attacker who has gained admin credentials knows there's a drift
  detector. They can compute the fingerprint, mutate the schema to match a
  previous known fingerprint (replay an old schema state), and the CI
  drift detector would see no drift.
- The function's *intentional* purpose (fingerprint for drift detection) is
  silently defeatable by an admin who knows the algorithm.

## Recommendation

- Make the function `SECURITY INVOKER` and `STABLE` so the caller's grants
  are used (still admin-only, but no privilege escalation).
- Record a `phi_audit_log` row on each call.
- Add a separate service-role-only RPC for the CI drift job; the
  authenticated-admin path should be a thin wrapper.
