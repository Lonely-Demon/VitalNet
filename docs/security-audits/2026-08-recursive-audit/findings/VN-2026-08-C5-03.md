# VN-2026-08-C5-03 — JWKS fetcher is not bounded; a malicious or compromised auth server can return a huge JWKS

**Severity:** MEDIUM
**Status:** OPEN
**Location:** `apps/api/supabase/functions/api/_shared/auth.ts:28-36`
**Component:** apps/api
**Category:** DoS via dependency trust

## Evidence

```ts
let remoteJwks: ReturnType<typeof createRemoteJWKSet> | null = null;

function getRemoteJwks() {
  if (!remoteJwks) {
    const config = getConfig();
    remoteJwks = createRemoteJWKSet(new URL(`${config.supabaseUrl}/auth/v1/.well-known/jwks.json`));
  }
  return remoteJwks;
}
```

`createRemoteJWKSet` from `jose` fetches the JWKS once and caches it.
The cache duration is controlled by `cacheMaxAge` (default 10 minutes)
and `cooldownDuration` (default 30 seconds). A Supabase auth server is
trusted, but the URL is `config.supabaseUrl` — which is operator-set
during deploy.

If the `supabaseUrl` is misconfigured to a non-Supabase endpoint
(operator typo, malicious env var injection), the JWKS fetcher will
hit a foreign server, cache whatever JWKS that server returns, and
trust its public keys. A malicious JWKS server can:
- Return a public key the attacker has the private key for → forge
  any token.
- Return a JWKS with millions of keys → blow up memory.
- Return a JWKS with a 1-million-byte response → slow token verification.

## Risk (chained attack)

1. Attacker compromises the deploy pipeline (e.g., a malicious
   dependency update that overwrites `SUPABASE_URL`).
2. `supabaseUrl` is now `https://attacker.example/`.
3. Edge function starts, calls `getRemoteJwks()` on first request.
4. JWKS is fetched, cached.
5. Attacker can now mint JWTs that pass signature verification.

The defence is the HS256 fast path: if `config.jwtLocalVerification`
is true, the HS256 decode runs first. Only if HS256 fails does the
remote JWKS verify. So an attacker must forge an HS256-signed token
*and* an asymmetric-signed token to succeed. HS256 is bound to
`SUPABASE_JWT_SECRET`, which is a separate secret.

But if the operator's project uses asymmetric keys (Supabase's
default for new projects since 2024), `config.jwtLocalVerification`
still tries HS256, fails, and falls through to JWKS — which trusts
the attacker-controlled URL.

## Recommendation

1. Validate `config.supabaseUrl` at boot: must end in `.supabase.co`
   (or a project-specific override), must be HTTPS, must match a
   known project reference.
2. Pin the JWKS endpoint to `https://${projectRef}.supabase.co/auth/v1/.well-known/jwks.json`
   where `projectRef` is the canonical project ref.
3. Cap the JWKS response size (jose's `createRemoteJWKSet` accepts
   `timeoutDuration`; set a small one).
4. Add a CI check that `config.supabaseUrl` is HTTPS and a Supabase
   domain.
