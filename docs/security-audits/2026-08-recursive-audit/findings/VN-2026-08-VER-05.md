# VN-2026-08-VER-05 — Transient profile resolution fail-open (CONFIRMED)

**Severity:** MEDIUM
**Status:** OPEN
**Location:** `backend/app/core/auth.py:133-138`
**Component:** Backend auth
**Category:** Fail-open on auth subsystem failure

## Evidence

```python
# auth.py:133-138
except Exception:
    # Transient failure — do not cache; fall back to last known state.
    if cached:
        return cached[1], cached[2], cached[3]
    return True, "", None
```

When `_resolve_profile` is called for a user with no cached entry and the
profiles-table query fails (DB outage, network glitch, table-missing), the
function returns `(is_active=True, role="", facility_id=None)`.

`is_active=True` means `get_current_user` does *not* raise the
`"Account is deactivated or not provisioned"` 403 — the user is treated as
provisioned. `role=""` means `require_role` is bypassed (no role matches
the allowed list), and `facility_id=None` means the user is unscoped
(treated as global per the codebase's "no facility = global" convention
in some routes).

## Risk (chained attack)

This is the classic "fail open under failure" pattern. An attacker who can
induce a transient DB blip at the right moment gets an unauthenticated
authentication. More realistically:

1. Attacker is a former employee with a revoked Supabase auth.users row but
   a still-valid token (revocation is checked against the profiles table).
2. They time their request during a known DB blip.
3. The cache miss + DB error path returns `is_active=True`, role="".
4. The route handler that uses `get_current_user` *without* `require_role`
   (and there are several — see, e.g., `soft_delete_case` which uses
   `require_role("admin", "doctor", "asha_worker")` but the role check
   fails on `""` and returns 403, but other handlers like
   `case_patient_summary` only check role inside the handler logic).

Actually — most routes use `require_role`, and `""` fails every role check.
But:

- A route that doesn't use `require_role` (and there are some) and uses
  `get_current_user` directly will treat the user as valid.
- The `submit_case` route uses `require_role("asha_worker", "admin")` — `""`
  fails. The user gets a 403, which is correct.
- But `_authorize_case_row_access` checks `role = _resolved_role(user)`
  which is `""`. The `asha_worker` branch checks
  `row.get("submitted_by") == user_id` and would only allow if the row was
  submitted by the same user. Combined with `facility_id = None`, doctor
  branch fails (no facility match). Admin branch would succeed if the role
  were "admin" — but role is `""`, so admin branch fails too.

So in practice, the fail-open state is benign in the current code because
`""` fails most role-gated branches. But the **principle** is wrong: an
auth subsystem should fail closed, not open.

## Recommendation

```python
except Exception:
    if cached:
        return cached[1], cached[2], cached[3]
    return False, "", None  # was True, "", None — fail closed
```

The cache (when present) provides a reasonable last-known-state fallback;
without a cache, the only safe answer is "I cannot determine — deny".
