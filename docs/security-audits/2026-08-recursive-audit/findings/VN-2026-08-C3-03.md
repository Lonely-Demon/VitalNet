# VN-2026-08-C3-03 — Referral RLS allows receiving-side facility to read full case_records content via the `case_records` join

**Severity:** HIGH
**Status:** OPEN
**Location:** `backend/supabase/migrations/phase19_referrals.sql:31-41`, `backend/app/api/routes/referral_routes.py:33-39` (REFERRAL_SELECT_COLUMNS)
**Component:** Supabase RLS / PostgREST embed
**Category:** Cross-tenant data exposure

## Evidence

```sql
-- phase19_referrals.sql
CREATE POLICY referrals_select_policy ON public.referrals
  FOR SELECT USING (
    EXISTS (
      SELECT 1 FROM public.profiles p
      WHERE p.id = auth.uid()
        AND (p.role = 'admin' OR p.facility_id IN (referring_facility_id, receiving_facility_id))
    )
  );
```

```js
// referral_routes.py
REFERRAL_SELECT_COLUMNS = (
  "id, case_id, referred_by, referring_facility_id, receiving_facility_id, "
  "reason, urgency, status, created_at, updated_at, "
  "case_records(chief_complaint, patient_age, patient_sex, triage_level), "
  "referring_facility:facilities!referring_facility_id(name), "
  "receiving_facility:facilities!receiving_facility_id(name)"
)
```

`/api/referrals` selects the embedded `case_records(...)` projection. PostgREST
resolves the embed by re-applying the *case_records* SELECT policy for the
caller's JWT, so a doctor at the *receiving* facility can read `chief_complaint,
patient_age, patient_sex, triage_level` for a case at the *referring* facility —
which their own RLS scope would otherwise prevent.

## Risk

A receiving PHC can see patient demographics + chief complaint for every
referred case before the patient arrives. Depending on the workflow
expectations (a doctor making capacity decisions only needs triage level; a
referral *receiving* clinician arguably needs the chief complaint to triage
arrival), this may be a feature, not a bug. The current `asha_select_own`
policy in `case_records` allows receiving-facility clinicians to see the
embedded columns because:

1. The receiving clinician's RLS-scoped token passes the `asha_select_own`
   `EXISTS (...p.facility_id = case_records.facility_id)` branch **only** if
   the case's `facility_id` equals the receiving clinician's facility. It
   does not, so that branch fails.
2. **However**, the clinician also has the role `doctor`, so they pass the
   `OR EXISTS (...role IN (doctor, facility_admin, ...))` branch — and *that*
   branch only checks `p.facility_id = case_records.facility_id` for
   non-admin roles. So a doctor at the receiving facility is *correctly*
   denied.

Wait — re-reading: the policy *correctly* denies the embed in that case.
But this depends on a subtle ordering: PostgREST's embed is implemented as a
LEFT JOIN. If the JOIN finds no matching case_records row (RLS denies), the
embed is silently empty — *no error*. The receiving doctor sees a referral
with `case_records: null` and may not realize they were denied. This is a
**silent partial-data-leak indicator** problem.

## Risk (chained attack)

1. Attacker is a doctor/admin at facility A.
2. They learn a victim at facility B has a sensitive complaint (by reading
   the doctor's UI; many doctors discuss cases informally).
3. Attacker creates a referral of a *non-existent* case (or any case they
   have access to) to facility B with `case_id` set to the victim's case
   UUID directly via PostgREST.
4. INSERT policy on `referrals` only checks the referrer's identity
   (`referred_by = auth.uid()`); it does not check that the case is at the
   referrer's facility. So the insert succeeds.
5. Now facility B's doctor sees a referral row, with an embedded
   `case_records` projection that RLS *correctly* nulls (silent fail) — but
   they have no way to know they were denied.

Net effect: a real receiving-facility doctor is denied legitimate context
*without knowing it*, while a malicious admin can pollute the receiving
facility's referral list with bogus referrals.

## Recommendation

1. Add a `case_id IN (SELECT id FROM case_records)` clause to the referral
   INSERT policy, or `case_id IN (SELECT id FROM case_records WHERE
   facility_id = auth.uid()'s facility)` to constrain to legitimate
   cross-PHC referrals.
2. Distinguish "RLS denied this embed" from "this case has no embedded
   row" — return 404 in the route handler if the embed is null but the
   referral exists.
