# VN-2026-08-C9-02 — SlowAPI rate limiter is per-process by default; horizontally-scaled deployments do not share state

**Severity:** MEDIUM
**Status:** OPEN (acknowledged in code; not enforced)
**Location:** `backend/app/core/config.py:40-45`, `backend/app/api/routes/cases.py:44-50`
**Component:** Backend / Rate limiting
**Category:** DoS via horizontal scale

## Evidence

```python
# config.py:40-45
# slowapi storage backend. Empty = in-memory (per-process, resets on restart,
# NOT shared across horizontally-scaled instances). Set to a shared store
# (e.g. "redis://host:6379") in production multi-instance deployments so the
# limit is enforced globally.
rate_limit_storage_uri: str = ""
```

```python
# cases.py:44-50
_limiter_kwargs = {"key_func": _get_user_id}
if settings.rate_limit_storage_uri:
    _limiter_kwargs["storage_uri"] = settings.rate_limit_storage_uri
limiter = Limiter(**_limiter_kwargs)
```

The default is the per-process in-memory store. The code documents
"set a shared store in production multi-instance deployments" but
does not enforce it.

## Risk (chained attack)

1. The backend is deployed with N uvicorn workers (or N containers)
   for production load.
2. Each worker has its own in-memory rate-limit counter.
3. An attacker sending `submit_case` requests at the per-worker limit
   (e.g., 20/min per worker) bypasses the global limit by N×
   (e.g., 20*60 = 1200/min for N=1, or 20*60*N for N workers).
4. The attacker can drive enough LLM calls through Groq to:
   - Run up a non-trivial bill (LLM cost DoS).
   - Or trigger the Groq API rate limit, which would also block
     legitimate requests.

The 5-line code comment is correct; the gap is that the production
deployment *might* forget to set the env var, and there is no
startup check.

## Recommendation

1. Refuse to start in `environment == "production"` with
   `rate_limit_storage_uri == ""`. Log loudly and exit.
2. The same is true of the `data_retention_days` (set to 0 disables
   the endpoint; production should require a non-zero value or
   an explicit "no retention" flag).
3. Document the requirement in `setup.sh` and the deployment
   checklist.
