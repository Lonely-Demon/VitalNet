# VN-2026-08-C5-02 — `c.res.clone().json()` may double-consume the response body; idempotent retry may return the stored replay twice

**Severity:** MEDIUM
**Status:** OPEN
**Location:** `apps/api/supabase/functions/api/_shared/idempotency.ts:62-76`
**Component:** apps/api
**Category:** Streaming response bug

## Evidence

```ts
await next();
if (c.res.status >= 200 && c.res.status < 300) {
  try {
    const body = await c.res.clone().json();
    const { error: recordError } = await db.rpc("fn_client_event_record", {
      p_event_id: eventId,
      p_event_type: eventType,
      p_response: body,
    });
```

Hono's `Response.clone()` is the standard Web API `Response.clone()`,
which creates a tee. The `await c.res.clone().json()` reads from the
clone, leaving the original `c.res` body intact. This is correct in
theory.

The issue: in the existing routes, the handler also returns a
`c.json(...)` which sets `c.res` to a fresh `Response` object whose
body is a *fresh* `ReadableStream`. The `clone()` of a `Response` is
allowed exactly once; after the first `.json()` call, the original is
still consumable. This works in modern Deno (verified in Hono v4+).

But the `db.rpc("fn_client_event_record", { p_response: body })` is
called *after* `await next()` returns. By that time, the response has
already been *sent* to the client (Hono v4 streams the response
immediately after the handler returns; it doesn't wait for the
idempotency middleware to finish). The `c.res.clone().json()` call may
read a *streamed-and-then-torn-down* body, throwing a `TypeError:
body unusable` that is silently swallowed by the try/catch.

## Risk (chained attack)

1. A successful first request records the event in `client_events`.
2. A retry replays the stored response — correct.
3. A *different* retry of the same event id but with a *new* request body
   is rejected by `case_records.client_id`'s unique constraint, but the
   LLM briefing and SHAP are re-computed because the idempotency replay
   path is not taken (e.g., the lookup fails open per line 52-55). The
   briefing is *not* stored because the response body wasn't readable.
4. The next retry sees no stored replay (because the recording failed
   silently), re-runs the full pipeline, and the LLM cost is paid again.

This is more of a correctness/efficiency issue than a security one —
but it interacts with the LLM cost model: a malicious caller can
intentionally retry with malformed bodies to drive up LLM cost.

## Recommendation

1. Record `client_events` *before* calling `next()`, not after:
   ```ts
   const user = c.get("user");
   const db = getSupabaseForUser(user.token);
   // First-time event: insert a placeholder row, then call next(),
   // then update the row with the actual response.
   ```
   This is the standard idempotency-middleware pattern.
2. Or, use a Hono `c.set("responseBody", body)` in the handler and
   read it in the middleware.
3. Add a regression test that retries a successful request and
   asserts the LLM is *not* called twice (mock the LLM, count
   invocations).
