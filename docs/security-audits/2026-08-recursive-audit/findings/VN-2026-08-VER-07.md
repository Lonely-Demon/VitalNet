# VN-2026-08-VER-07 — Live database still has the `user_metadata` RLS policies that phase32 was supposed to DROP (CRITICAL, NEW DISCOVERY)

**Severity:** CRITICAL
**Status:** OPEN
**Location:** `backend/supabase/schema_snapshot.sql:364, 365, 375, 376, 377, 397`
**Component:** Supabase RLS / live database
**Category:** Re-introduced privilege escalation vulnerability

## Evidence

`phase32_fix_jwt_metadata_rls_vulnerability.sql` (in tracked migrations) explicitly
DROPs three policies on `case_records` and one on `profiles` that used the
`auth.jwt() -> 'user_metadata'` pattern. From the phase32 file header:

> Found during a schema-drift testing pass (docs/DECISIONS.md) via a live schema
> capture: three policies on active tables (case_records, profiles) used
> this pattern; all are either redundant with an existing safe policy or
> rewritten below to use the table-lookup pattern.

The phase32 fix:
- DROPs `doctor_update` on `case_records`
- DROPs `asha_select_own` on `case_records` and recreates it
- DROPs `profile_select` on `profiles`

The live database (`schema_snapshot.sql`) still has all of them:

```sql
-- schema_snapshot.sql:364
CREATE POLICY doctor_update ON public.case_records AS PERMISSIVE FOR UPDATE TO public
  USING ((((auth.jwt() -> 'user_metadata'::text) ->> 'role'::text) = ANY (ARRAY['doctor'::text, 'admin'::text])));

-- schema_snapshot.sql:365
CREATE POLICY asha_select_own ON public.case_records AS PERMISSIVE FOR SELECT TO public
  USING (((deleted_at IS NULL) AND ((submitted_by = auth.uid()) OR (((auth.jwt() -> 'user_metadata'::text) ->> 'role'::text) = ANY (ARRAY['doctor'::text, 'admin'::text])))));

-- schema_snapshot.sql:375-377
CREATE POLICY "Doctors can create referrals from their facility" ON public.case_referrals AS PERMISSIVE FOR INSERT TO public
  WITH CHECK (((from_facility = (((auth.jwt() -> 'user_metadata'::text) ->> 'facility_id'::text))::uuid) AND (((auth.jwt() -> 'user_metadata'::text) ->> 'role'::text) = ANY (ARRAY['doctor'::text, 'facility_admin'::text, 'admin'::text, 'super_admin'::text]))));
-- ... 376, 377 similar

-- schema_snapshot.sql:397
CREATE POLICY profile_select ON public.profiles AS PERMISSIVE FOR SELECT TO public
  USING (((id = auth.uid()) OR (((auth.jwt() -> 'user_metadata'::text) ->> 'role'::text) = 'admin'::text)));
```

## Risk (chained attack — CRITICAL)

`user_metadata` is **client-settable** in Supabase. Any authenticated user can
`PUT /auth/v1/user` with `{"data": {"role": "admin", "facility_id": "<any UUID>"}}`
and the JWT will carry the new claim on the next refresh.

Combined with the live policies, the attacker can:

1. Set their own `user_metadata.role = 'admin'` via `PUT /auth/v1/user`.
2. Their JWT now carries `user_metadata.role = 'admin'`.
3. The `asha_select_own` policy (line 365) uses `user_metadata.role` in the
   `OR EXISTS` branch — the attacker now passes the "doctor/admin" branch
   and can SELECT every case across every facility.
4. The `doctor_update` policy (line 364) lets the attacker UPDATE every
   case row.
5. The `profile_select` policy (line 397) lets the attacker SELECT every
   profile (including the service-role key custodian's profile).
6. The `case_referrals` policies (lines 375-377) let the attacker
   create/update referrals with arbitrary `from_facility` / `to_facility`,
   bypassing the real RLS-scoped `referrals` table from phase19.

This is the **EXACT** privilege-escalation vulnerability that phase32 was
written to fix. Either:
- The drift detector (`fn_schema_fingerprint`) is not running against
  the live database and the team doesn't know the policies are still
  there, or
- The drift detector IS running and alerting, but no one has acted
  (no remediation recorded in the `fixes/` directory), or
- phase32 was never actually run on the live database.

The drift-detection CI workflow (`db-schema-drift.yml`) is the early-
warning system. It should have caught this. Verifying that the
workflow has actually been run recently is a sub-investigation worth
its own audit.

## Recommendation

1. **Immediate**: Run the phase32 DROP statements against the live
   database. They are idempotent (`DROP POLICY IF EXISTS ...`).
2. **Track**: This drift is now tracked — add a new migration
   `phase42_force_drop_untracked_metadata_policies.sql` that does
   the DROP and re-runs `fn_schema_fingerprint` to verify.
3. **Improve the drift detector**: The current
   `fn_schema_fingerprint` returns a single MD5 — the team must
   diff against a known-good to know *what* drifted. Add a structured
   drift report that names the policies/columns that differ.
4. **CI gate**: Make the schema-drift workflow a *required check* on
   every PR, not a scheduled job. A scheduled job is reactive (a
   week after the drift); a PR-time check is proactive.
